# Diary AI 트러블슈팅

개발하면서 발견한 문제와 고친 과정을 기록했습니다. 1번과 7번은 제가 먼저 궁금해서 시작했고, 나머지는 기능을 만든 뒤 AI에게 코드를 보여 주고 리뷰를 받으면서 찾았습니다.
항목마다 어떻게 발견하고 확인했는지 함께 적었습니다.

## 1. 다이어리 목록 조회 성능 개선 (복합 인덱스)

다이어리가 적을 때는 인덱스 없이 테이블 전체를 읽어도(풀 스캔) 괜찮을 것 같다고 생각했습니다. 다만 다이어리가 많아지면 목록 조회에 얼마나 걸릴지 궁금해서, 로컬 DB에 데이터를 넣고 측정했습니다.
당시 `diaries`에는 기본 키 인덱스만 있어서 사용자별 목록을 찾으려면 테이블 전체를 읽어야 했습니다.

`userId`만 인덱스에 넣으면 사용자별로 다이어리를 빠르게 찾을 수 있지만, 목록은 최신 날짜순으로 보여 줘야 해서 찾은 결과를 매번 날짜순으로 다시 정렬해야 합니다. 그래서 `(userId, diaryDate)` 순서로
[복합 인덱스](../src/migrations/1791653488772-AddDiaryUserDiaryDateIndex.ts)를 만들어, 한 사용자의 데이터를 이미 정렬된 순서로 읽을 수 있게 했습니다.
다이어리를 추가하거나 날짜를 바꿀 때(`INSERT`, `UPDATE`) PostgreSQL이 인덱스도 함께 갱신해야 해서 쓰기 작업이 조금 늘어납니다. 대신 조회할 때는 따로 정렬하지 않고 바로 읽을 수 있어서 조회가 빨라질 거라고 예상했습니다.
다이어리는 쓰기보다 목록 조회가 훨씬 많을 거라고 봐서 목록 조회를 먼저 개선하기로 했습니다.

로컬 PostgreSQL 17의 다이어리 100,003건 중 한 사용자의 101건을 조회했습니다. `EXPLAIN (ANALYZE, BUFFERS)`의 실행 시간을 적용 전후 5번씩 기록했습니다.

|        |          적용 전 |        적용 후 |
| ------ | ---------------: | -------------: |
| 평균   |        15.952 ms |       0.278 ms |
| 중앙값 |        13.740 ms |       0.249 ms |
| 범위   | 11.378~21.507 ms | 0.064~0.591 ms |

이 수치는 페이지 처리(`LIMIT/OFFSET`)와 전체 건수 조회(`COUNT`)를 뺀 SQL 실행 시간입니다. 실행 시간은 기록했지만 실행 계획은 기록하지 못했고 DB가 메모리에 들고 있는 데이터(캐시) 상태도 맞추지 않았습니다.
다시 측정할 때는 목록 API가 실행하는 SQL 그대로 비교하고 실행 계획도 함께 남길 생각입니다.

## 2. AI 분석 중복 요청으로 인한 OpenAI 중복 호출

백엔드 프로젝트 경험이 없어서 기능을 만든 뒤 AI에게 코드를 보여 주고 운영에서 생길 수 있는 문제를 물어보며 하나씩 확인했습니다. 그중 "같은 다이어리에 분석 요청이 동시에 들어오면 OpenAI가 두 번 호출될 수 있다"는 지적이 있었습니다.

처음에는 저장된 분석이 있는지 조회하고 없으면 OpenAI를 호출한 뒤 결과를 저장했습니다. 두 요청이 모두 저장 전에 조회하면 둘 다 분석이 없다고 보고 각자 호출합니다. `diary_analyses.diaryId`에 UNIQUE 제약이 있어
두 번째 분석 저장은 실패하지만 그때는 이미 OpenAI 비용이 두 번 나간 뒤입니다.

실제 서비스에서 자주 일어날 일은 아니라고 봤습니다. 다만 조회와 저장 사이에 OpenAI 응답을 기다리는 시간이 있어서, 그사이 같은 다이어리의 분석 요청이 끼어들 수는 있었습니다. 저는 분석 버튼을 빠르게 여러 번 누르는 경우만 떠올렸고,
프론트에서 버튼을 비활성화하면 충분하다고 생각했습니다. 그런데 분석을 기다리다 화면을 나갔다 들어와 다시 누르거나, 네트워크가 불안정해 요청이 다시 가는 경우도 있다고 AI가 짚어 줬습니다.
자주 일어나지 않는 일이라도 비용이 드는 문제라서 서버에서 막기로 했습니다.

AI는 DB 행 잠금(`SELECT FOR UPDATE`)과 Redis 분산 락 같은 방법을 제시해 줬습니다. 당시에는 Redis를 쓰지 않아서, 락 하나 때문에 Redis를 새로 들이는 건 이 프로젝트에 과하다고 판단했습니다.
`SELECT FOR UPDATE`는 OpenAI 응답을 기다리는 동안 DB 연결(커넥션)을 계속 잡고 있어야 해서 고르지 않았습니다. 그래서 DB의 조건부 `UPDATE`로 분석 상태를 바꾸는 방식으로 결정했습니다.

다이어리의 분석 상태를 `IDLE`에서 `PROCESSING`으로 바꾸는 조건부 `UPDATE`를 추가했습니다. 실제로 행을 바꾼 요청만 분석을 진행하고, 나머지 요청은 `409`를 받습니다.
다만 처음 조회한 뒤 락을 잡기 전 사이에, 다른 요청이 분석을 끝내고 락을 풀었을 수도 있습니다. 그래서 락을 잡은 직후 분석 결과를 한 번 더 조회하고, 이미 분석 결과가 있으면 OpenAI를 호출하지 않고 그 결과를 돌려줍니다.

Jest에서는 락을 누가 잡을지 Mock으로 정해 두고 같은 다이어리로 분석 서비스를 두 번 동시에 호출해, 락을 얻지 못한 요청이 OpenAI를 호출하지 않는지 확인했습니다.
사람이 분석을 정확히 동시에 요청하기는 어려워서, 실제 DB에서 락이 동작하는지는 AI에게 임시 스크립트를 만들어 실행하게 해서 확인했습니다. 실제 PostgreSQL에서 분석을 10번 동시에 호출한 결과는 [3번](#3-서버-장애-시-분석-락이-해제되지-않는-문제)에 정리했습니다.

## 3. 서버 장애 시 분석 락이 해제되지 않는 문제

2번에서 락을 만든 뒤 AI에게 이 방식의 약점을 물었더니, 서버가 분석 도중 멈추면 락이 풀리지 않을 수 있다는 지적이 있었습니다. 고치기 전 상태를 직접 재현하지는 않았습니다. 다만 EC2에 수동으로 배포하고 있어서,
분석 중에 서버를 다시 띄우면 충분히 생길 수 있는 상황이라고 봤습니다.

락을 `finally`에서 풀어도, 서버가 중간에 종료되거나 해제 시 DB 연결이 끊기면 다이어리가 `PROCESSING`으로 남을 수 있었습니다.

`SELECT FOR UPDATE`였다면 서버가 멈췄을 때 잠금이 알아서 풀립니다. 이 잠금은 트랜잭션이 끝날 때까지 유지되는데, 서버가 멈춰 DB 연결이 끊기면 PostgreSQL에서 트랜잭션을 취소하면서 잠금도 함께 풀기 때문입니다.
하지만 같은 이유로 OpenAI 응답을 기다리는 동안 DB 연결을 계속 잡고 있어야 해서 이 방법 대신 상태 값을 DB에 저장하고, 쿼리가 끝나면 연결을 돌려주는 조건부 `UPDATE` 방식으로 정했습니다.
이 조건부 `UPDATE`는 서버가 멈추면 저장된 `PROCESSING`이 지워지지 않습니다. 그래서 상태와 함께 시작 시각(`analysisStartedAt`)을 기록하고, 만료 시간을 두기로 했습니다.

5분이 지나면 다른 요청이 락을 다시 잡을 수 있게 했습니다. OpenAI 호출은 타임아웃 60초, 자동 재시도 0회로 설정해 두어서, 정상적으로 진행 중인 분석의 락이 먼저 풀리지 않도록 그보다 넉넉하게 5분으로 정했습니다.
5분이 지나 다른 요청이 락을 다시 잡으면, 먼저 시작한 작업이 뒤늦게 끝나면서 새 작업의 락을 풀어 버릴 수 있습니다. 그래서 락을 잡을 때 받은 `analysisStartedAt`이 DB에 있는 값과 같을 때만 해제합니다.

OpenAI 호출이 실패하면 서버에 오류를 기록하고 클라이언트에는 `503`을 보냅니다. 이때도 분석 서비스의 `finally`에서 락 해제를 시도해 사용자가 다시 요청할 수 있게 했습니다.

2번과 3번은 AI에게 임시 스크립트 하나를 만들어 실행하게 해서 함께 확인했습니다. 손으로는 분석을 정확히 동시에 호출하거나, 락을 잡은 지 4분 59초 된 상황을 만들기 어려웠기 때문입니다. Redis 도입 전에 실행했고,
실제 서비스 코드와 실제 PostgreSQL 테스트 DB를 쓰되 OpenAI만 0.2초 걸리는 가짜 구현으로 바꿨습니다. HTTP 요청 대신 분석 서비스의 `createAnalysis()`를 `Promise.allSettled`로 동시에 호출했습니다.
이 스크립트는 저장소에 포함되어 있지 않습니다.

| 확인한 상황                         | 결과                                                                        |
| ----------------------------------- | --------------------------------------------------------------------------- |
| 같은 다이어리에 분석 10번 동시 호출 | 가짜 OpenAI 호출 1회, 409 예외(`ConflictException`) 9건, 마지막 상태 `IDLE` |
| 락을 잡은 지 4분 59초 / 5분 1초     | 재획득 실패 / 성공                                                          |
| 이전 작업이 새 작업의 락 해제 시도  | 새 작업의 락 유지                                                           |
| OpenAI 호출 실패                    | 503 예외, 저장된 분석 0건, 마지막 상태 `IDLE`                               |

단위 테스트는 락 획득 결과를 Mock으로 정해 서비스의 동작을 확인합니다. OpenAI 호출이 실패하면 분석을 저장하지 않고, 락을 잡을 때 기록한 시각으로 해제하는지도 확인합니다. AI가 `finishAnalysis()` 호출을 잠시 빼고 테스트를 돌려 보니 관련 테스트 2개가 실패했습니다.

## 4. 락 상태 변경이 다이어리 수정 시각을 바꾸는 문제

2번의 락을 AI로 만든 임시 스크립트로 실제 DB에서 테스트하던 중, AI가 실행된 SQL에 코드에 쓰지 않은 `"updatedAt" = CURRENT_TIMESTAMP`가 들어 있다고 짚어 줬습니다. 원인은 TypeORM의 `@UpdateDateColumn`으로, `update()`를 쓰면
수정 시각이 자동으로 함께 바뀝니다. 다이어리 응답에 `updatedAt`이 나가기 때문에, 글을 고치지 않고 분석만 했는데도 다시 조회하면 수정 시각이 바뀌어 있습니다.

락을 잡고 풀 때만 `updatedAt: () => '"updatedAt"'`을 넘겨 기존 값을 유지했습니다. 이 코드를 잠시 빼고 Postman으로 분석을 요청해 `updatedAt`이 바뀌는 것을 직접 재현했습니다. 고친 뒤 분석 성공·실패 후에도 수정 시각이 그대로인 것과,
사용자가 다이어리를 수정할 때는 갱신되는 것은 같은 임시 스크립트로 확인했습니다.

## 5. 다이어리 수정 시 기존 AI 분석과의 정합성

다이어리 수정과 AI 분석이 겹칠 때 생길 수 있는 문제를 AI가 짚어 줬습니다.

처음에는 본문을 수정하면 같은 트랜잭션에서 기존 분석을 지웠습니다. 그런데 분석이 진행되는 도중에 본문을 수정하면, 수정 전 본문으로 만든 분석이 수정 뒤에 저장될 수 있었습니다.

제목만 수정할 때도 문제가 있었습니다. TypeORM의 `save()`는 미리 읽어 둔 다이어리 객체를 DB 값과 비교해, 달라진 컬럼을 객체의 값으로 덮어씁니다. 그사이 다른 요청이 분석 락을 잡았다면, 읽어 둔 예전 상태(`IDLE`)로 락을 덮어쓸 수 있었습니다.

저는 분석 중에는 화면에 로딩 표시를 띄워 다른 클릭을 막아 두면, 분석 도중 본문을 바꾸는 일은 거의 없을 거라고 생각해 AI에게 다시 물었습니다. 하지만 다른 탭이나 기기에서 수정하거나 API를 직접 호출하면 화면에서 막은 것과 상관없이 요청이 들어올 수 있다고 해서,
서버에서도 막기로 했습니다.

수정 트랜잭션에서 다이어리 행을 잠그고, 분석 중(락을 잡은 지 5분이 안 됐을 때)에는 본문 변경에 `409`를 보냅니다. 제목과 날짜는 수정할 수 있습니다. 저장에는 `update()`를 써서 요청으로 받은 필드만 바꾸고, 분석 요청은 락을 잡은 뒤 본문을 다시 읽습니다.
분석 결과를 저장할 때 수정 여부를 확인하는 방법도 생각했지만, 그때는 이미 OpenAI 호출 비용이 든 뒤라 본문 변경을 먼저 막기로 했습니다.

[단위 테스트](../src/diary/diary.service.spec.ts)에서는 제목만 바꾸면 분석이 남고, 본문을 바꾸면 분석이 삭제되는지 확인했습니다. 분석 중 본문 수정이 거절되는 경우와 만료 후 수정이 허용되는 경우는 실제 DB 검증이 남아 있습니다.

## 6. DB UNIQUE 위반이 500으로 응답되는 문제 (전역 예외 필터)

같은 이메일로 동시에 가입하면 두 요청이 모두 사전 중복 조회를 통과할 수 있다고 AI가 짚어 줬습니다. 먼저 저장한 요청은 성공하고, 나머지는 DB의 UNIQUE 제약에 걸립니다. 처음에는 이 예외가 `500`으로 응답됐습니다.

전역 예외 필터에서 PostgreSQL의 UNIQUE 위반 코드 `23505`를 `409`로 바꿨습니다. 여러 저장 경로에 같은 예외 처리를 반복하지 않아도 됩니다. 응답에 요청 경로와 시각도 추가해 클라이언트에서 받은 에러를 서버 기록과 맞춰 보기 쉽게 했습니다.

사람이 두 요청을 정확히 동시에 보내기 어려워서, AI에게 curl로 같은 이메일의 가입 요청 두 개를 동시에 보내게 해 `201` 한 건과 `409` 한 건을 확인했습니다.

## 7. IP 기반 요청 제한으로는 사용자별 OpenAI 비용을 통제할 수 없는 문제

분석 API에는 원래 IP 기준 요청 제한만 있었습니다. IP로만 세면 회사나 학교처럼 같은 IP를 쓰는 사람들이 한도를 나눠 쓰게 된다고 생각했고, Throttler의 `getTracker`를 바꿔 사용자별로 세는 방법을 떠올렸습니다.
그런데 AI가 Throttler는 HTTP 요청 수를 센다고 알려 줬습니다. 그러면 저장된 분석을 돌려주는 요청이나 `409`를 받는 요청처럼 OpenAI를 호출하지 않는 요청도 횟수에 들어갑니다. 제가 막고 싶은 건 요청 수가 아니라 OpenAI 비용이라서,
실제로 호출하기 직전에 세기로 했습니다.

IP 제한은 짧은 시간에 몰리는 요청을 막는 용도로 그대로 두고, OpenAI 호출 직전에 Redis에서 사용자별 횟수를 세도록 했습니다. 첫 호출부터 24시간 동안 사용자당 10회까지 허용합니다.
`INCR`과 `EXPIRE`를 따로 실행하면 두 명령 사이에 서버가 멈춰 만료 시간이 없는 키가 남을 수 있어서, [Redis 문서의 예제](https://redis.io/docs/latest/commands/incr/)처럼 Lua 스크립트 한 번으로 묶었습니다.

Postman에서 한도를 임시로 2회로 낮추고 서로 다른 다이어리 3개를 분석했습니다. 앞의 두 요청은 `200`, 세 번째는 `429`를 받았습니다. 실제 Redis에서 동시 요청과 TTL을 확인하는 자동 테스트는 아직 없습니다.

현재는 OpenAI 호출 전에 횟수를 차감하고 실패해도 돌려주지 않습니다. 24시간 구간이 바뀌기 직전과 직후에는 짧은 시간에 최대 19번 호출할 수 있습니다. Redis 오류가 나면 OpenAI 호출을 막으며,
Redis 데이터 보존을 별도로 설정하지 않아 컨테이너를 다시 만들면 횟수가 초기화될 수 있습니다.

## 8. 로그아웃 후 refresh 토큰 해시가 다시 저장되는 문제

README의 남은 작업을 정리하다가, AI가 코드를 보고 토큰 재발급과 로그아웃이 겹치면 문제가 생길 수 있다고 했습니다.

토큰을 재발급할 때는 먼저 DB에서 refresh 토큰 해시를 읽고, 요청으로 받은 토큰과 맞는지 Argon2로 확인합니다. 이때 검증하는 사이에 로그아웃을 하면 문제가 생길 수 있었습니다. 로그아웃이 해시를 지웠는데도,
이미 진행 중이던 재발급이 뒤늦게 새 해시를 저장할 수 있었기 때문입니다. 이 순서로 처리되면 로그아웃한 뒤에도 새로 받은 refresh 토큰으로 다시 재발급이 가능해집니다.

그래서 검증에 사용한 해시가 DB에 그대로 있을 때만 새 해시를 저장하도록 바꿨습니다. `UPDATE`의 조건에 사용자 ID와 기존 해시를 함께 넣었습니다. 로그아웃이 먼저 해시를 지웠다면 조건에 맞는 행이 없어서 저장되지 않고,
서버는 `401`을 반환합니다. 두 재발급 요청이 같은 해시를 읽었을 때도 먼저 해시를 바꾼 요청만 성공합니다. [2번의 AI 분석 중복 요청 방지](#2-ai-분석-중복-요청으로-인한-openai-중복-호출)에서 쓴 조건부 `UPDATE`를 여기에도 적용했습니다.

Jest 단위 테스트에서는 해시를 바꾸지 못한 상황을 만들어 재발급이 거절되는지 확인했습니다. 저장 함수에 넘긴 해시가 새 refresh 토큰과 일치하는지도 확인했습니다. 실제 PostgreSQL에서 로그아웃과 재발급이 겹치는 경우는 아직 테스트하지 않았습니다.
