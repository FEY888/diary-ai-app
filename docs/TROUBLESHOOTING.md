## 1. 다이어리 목록 조회 성능 개선 (복합 인덱스)

> 관련 커밋: `620ded8 perf: 다이어리 목록 조회 복합 인덱스(userId, diaryDate) 적용 및 성능 측정`

### 문제

다이어리 목록 API(`GET /diaries`)는 로그인한 사용자의 다이어리만 `diaryDate` 내림차순으로 반환합니다.

```ts
// src/diary/diary.service.ts - diaryFindAll()
this.diaryRepository.findAndCount({
  where: { user: { id: userId } },
  skip: take * (page - 1),
  take,
  order: { diaryDate: 'DESC' },
});
```

운영 중 장애가 난 것은 아닙니다. 다이어리는 사용자 수와 작성 기간에 비례해 계속 쌓이는 테이블이고, 목록 조회는 가장 자주 호출되는 API입니다. 그래서 데이터가 많아졌을 때의 비용을 미리 측정했습니다.

### 원인 분석

스키마 확인: 인덱스 추가 전 `diaries` 테이블의 인덱스는 PK(`id`) 하나뿐이었습니다.

```sql
-- src/migrations/1790704167958-InitialMigration.ts
CREATE TABLE "diaries" (..., "userId" uuid NOT NULL, CONSTRAINT "PK_..." PRIMARY KEY ("id"));
ALTER TABLE "diaries" ADD CONSTRAINT "FK_..." FOREIGN KEY ("userId") REFERENCES "users"("id") ON DELETE CASCADE;
```

- PostgreSQL은 FK를 만들 때 참조하는 쪽(`diaries.userId`)에 인덱스를 자동으로 만들지 않습니다. (참조되는 `users.id`는 PK라서 인덱스가 있음)
- 그래서 `WHERE "userId" = ?` 조건을 인덱스로 좁힐 수 없고, 조건에 맞는 행을 찾은 다음 `diaryDate`로 다시 정렬해야 합니다.

측정 결과로 확인한 것: 약 10만 건 중 101건을 조회하는 데 평균 15.952 ms가 걸렸습니다. (아래 성능 비교 표)

> 인덱스 적용 전후의 실행 계획 원문(Seq Scan / Index Scan, Sort 노드, Buffers)은 기록해 두지 않았습니다.
> 그래서 "전체 테이블을 순차 스캔했다"는 것은 스키마를 근거로 한 판단이고, 실행 계획으로 확인한 사실은 아닙니다. 재측정 계획은 아래 "재발 방지 및 추가 검증"에 정리했습니다.

### 해결

조회 조건(`userId`, 등치 비교)과 정렬 기준(`diaryDate`)을 순서대로 묶은 복합 인덱스를 마이그레이션으로 추가했습니다.

```ts
// src/diary/entities/diary.entity.ts
@Index('IDX_diaries_user_diary_date', ['user', 'diaryDate'])
```

```sql
-- src/migrations/1791653488772-AddDiaryUserDiaryDateIndex.ts
CREATE INDEX "IDX_diaries_user_diary_date" ON "diaries" ("userId", "diaryDate");
```

컬럼 순서를 `(userId, diaryDate)`로 정한 이유:

- B-tree 복합 인덱스는 앞 컬럼이 같은 값인 범위 안에서 뒤 컬럼 순서로 정렬되어 있습니다.
- `userId`를 등치 조건으로 고정하면, 해당 범위의 항목은 이미 `diaryDate` 순서입니다. 그래서 정렬 없이 인덱스 순서대로 읽을 수 있습니다.
- B-tree는 역방향으로도 읽을 수 있어서, `DESC` 정렬을 위해 `DESC` 인덱스를 따로 만들 필요가 없습니다.
- 순서를 반대로 `(diaryDate, userId)`로 두면 `userId`로 범위를 좁힐 수 없습니다.

### 개선 전후 성능 비교

**측정 조건**

| 항목        | 내용                                                                                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 환경        | 로컬 PostgreSQL (Docker `postgres:17`)                                                                                                                     |
| 데이터      | `diaries` 약 100,003건 (시드 99,900 + 대상 사용자 100 + 기존 3)                                                                                            |
| 대상        | 특정 사용자의 다이어리 101건                                                                                                                               |
| 데이터 생성 | [`seed-performance-data.sql`](../src/diary/sql/seed-performance-data.sql)                                                                                  |
| 측정        | `EXPLAIN (ANALYZE, BUFFERS)`의 Execution Time, 적용 전 · 후 각 5회                                                                                         |


| 한계                              | 영향                                                                                                                                       |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |

| 실행 계획 원문 미보관             | 어떤 스캔 방식으로 바뀌었는지 문서로 증명할 수 없습니다.                                                                                   |
| 캐시 상태 미통제                  | 적용 후 수치가 0.064~0.591 ms로 9배 이상 차이 납니다. 버퍼 캐시 상태에 따라 값이 달라졌을 가능성이 있습니다.                               |
| 로컬 단일 환경, 5회               | 운영 환경(RDS) 수치로 일반화할 수 없습니다.                                                                                                |
| DB 실행 시간만 측정               | 네트워크, 직렬화를 포함한 API 응답 시간은 측정하지 않았습니다.                                                                             |

### 의사결정과 트레이드오프

| 선택지                                | 판단                                                                                                                                                |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `userId` 단일 인덱스                  | 조건 필터는 되지만 `diaryDate` 정렬 단계가 남습니다.                                                                                                |
| **`(userId, diaryDate)` 복합 인덱스** | **선택.** 필터와 정렬을 인덱스 하나로 처리할 수 있습니다. 앞 컬럼이 `userId`라서 FK 조건만 쓰는 조회(사용자 삭제 시 CASCADE 등)에도 쓸 수 있습니다. |
| `(userId, diaryDate DESC)`            | B-tree는 역방향 스캔이 가능해서 이득이 없다고 판단했습니다.                                                                                         |
| 커버링 인덱스 (`INCLUDE`)             | 목록 응답에 `content`(text)가 포함되어 인덱스가 지나치게 커집니다.                                                                                  |

**비용**

- `INSERT`와 `userId` · `diaryDate` 변경 시 인덱스도 함께 갱신해야 해서 쓰기 비용과 저장 공간이 늘어납니다. 다이어리는 쓰기보다 조회가 많아 받아들일 수 있다고 판단했습니다.
- `CREATE INDEX`는 실행되는 동안 테이블 쓰기를 막습니다. 데이터가 많은 운영 DB라면 `CREATE INDEX CONCURRENTLY`가 필요합니다. (TypeORM 마이그레이션은 기본적으로 트랜잭션 안에서 실행되는데, `CONCURRENTLY`는 트랜잭션 안에서 쓸 수 없어 별도 처리가 필요합니다.)

**이 인덱스로 해결되지 않는 것**

- `OFFSET` 페이지네이션은 뒤 페이지로 갈수록 건너뛸 행을 모두 읽어야 합니다.
- `findAndCount()`는 요청마다 `COUNT(*)`를 실행합니다.
- 정렬 키가 `diaryDate` 하나라서 같은 날짜의 다이어리가 여러 개면 페이지 사이에서 순서가 바뀔 수 있습니다. `ORDER BY "diaryDate" DESC, id DESC`처럼 고유한 보조 정렬 키가 필요합니다.

### 재발 방지 및 추가 검증

**인덱스 관리 원칙**

- 스키마는 `synchronize: false`, 마이그레이션으로만 변경합니다. 인덱스도 엔티티의 `@Index`와 마이그레이션에 함께 남겨 코드에서 추적할 수 있게 했습니다.
- 새 조회 API를 만들 때 `WHERE` · `ORDER BY` 컬럼에 맞는 인덱스가 있는지 확인합니다. FK 컬럼에는 인덱스가 자동으로 생기지 않는다는 점을 함께 확인합니다.

**추가 검증 (예정)**

1. 실제 API 쿼리로 다시 측정: TypeORM 로그(`logging: true`)로 실제 SQL을 확인하고, `LIMIT 20 OFFSET 0`, 뒤쪽 페이지, `COUNT(*)`를 각각 측정합니다.
2. 실행 계획 원문 보관: 인덱스 적용 전후의 `EXPLAIN (ANALYZE, BUFFERS)` 출력 전체를 저장합니다.
3. 측정 조건 통일: 시드 후 `ANALYZE diaries;` 실행, 측정 전 동일 쿼리로 워밍업 후 N회 측정.
4. 인덱스 전후 비교는 운영 데이터가 없는 로컬 DB에서, 트랜잭션 안에서 인덱스를 지웠다가 되돌리는 방식으로 진행합니다.

```sql
-- 로컬 DB 전용: DROP INDEX도 트랜잭션 안에서 ROLLBACK 가능
BEGIN;
DROP INDEX "IDX_diaries_user_diary_date";
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM diaries WHERE "userId" = '<id>' ORDER BY "diaryDate" DESC LIMIT 20 OFFSET 0;
ROLLBACK;
```

## 2. AI 분석 중복 요청으로 인한 OpenAI 중복 호출

### 문제

같은 다이어리에 분석 요청이 동시에 들어오면, 두 요청이 모두 "기존 분석 없음"을 확인한 뒤
OpenAI를 각각 호출할 수 있었습니다. 외부 API 비용이 중복으로 발생합니다.

### 원인 분석

```
요청 A: findOne() → 분석 없음 ─┐
요청 B: findOne() → 분석 없음 ─┼→ 둘 다 OpenAI 호출
```

"조회"와 "분석 시작"이 분리되어 있어, 그 사이에 다른 요청이 끼어들 수 있었습니다.

### 해결

`diaries` 테이블에 `analysisStatus`(`IDLE` / `PROCESSING`) 컬럼을 두고,
PostgreSQL의 조건부 UPDATE로 분석 권한을 선점하도록 했습니다.

```sql
UPDATE diaries SET "analysisStatus" = 'PROCESSING'
WHERE id = :id AND "analysisStatus" = 'IDLE';
```

- UPDATE는 단일 문장으로 원자적으로 실행되므로, 동시에 실행되어도 `affected = 1`인 요청은 하나뿐입니다.
- 선점에 실패한 요청은 `409 Conflict`를 반환합니다.
- 선점에 성공한 요청은 분석이 끝나면 `finally`에서 `IDLE`로 되돌립니다.
- 선점 직후 기존 분석을 한 번 더 확인해, 직전에 다른 요청이 저장한 결과가 있으면 그대로 반환합니다.

이 방식을 적용한 뒤, 서버 장애 시 락이 해제되지 않는 문제를 발견했습니다 → [3번](#3-서버-장애-시-분석-락이-해제되지-않는-문제)

## 3. 서버 장애 시 분석 락이 해제되지 않는 문제

### 문제

락 해제가 애플리케이션의 `finally` 블록에만 의존하고 있었습니다.

```
tryStartAnalysis()     : IDLE → PROCESSING   (DB에 기록)
OpenAI 호출
finally finishAnalysis(): PROCESSING → IDLE   (애플리케이션이 실행)
```

아래 상황에서는 `finally`가 실행되지 않습니다.

- 배포 중 서버 재시작, 메모리 부족(OOM), 프로세스 강제 종료
- `finishAnalysis` 실행 시점의 DB 연결 끊김

그러면 해당 다이어리는 **영구히 `PROCESSING`으로 남고**, 이후 모든 분석 요청이 `409`를 받습니다.

### 원인 분석

락의 상태는 DB에 있지만, 락을 해제하는 주체는 애플리케이션 프로세스입니다.
락을 잡은 프로세스가 사라지면 해제할 주체도 사라지는데, 시간이 지나면 저절로 풀리는 장치가 없었습니다.

### 해결 방안 비교

| 방안                                  | 장점                                         | 단점                                                                                                                                |
| ------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 서버 시작 시 `PROCESSING` 일괄 초기화 | 구현이 간단                                  | 서버가 여러 대이면 다른 서버의 정상 작업까지 해제. DB 연결 끊김은 해결 못 함                                                        |
| PostgreSQL 행 락 / advisory lock      | 세션이 끊기면 자동 해제                      | OpenAI 응답을 기다리는 동안 DB 커넥션을 점유 → 커넥션 풀 고갈 위험                                                                  |
| Redis 락 (`SET NX EX`)                | TTL 락의 표준 구현                           | 당시에는 락 하나 때문에 인프라를 추가하기엔 과하다고 판단 (이후 호출 횟수 제한으로 Redis를 도입했지만 락은 옮기지 않음, README 6장) |
| **락 만료 시간(TTL) (선택)**          | 컬럼 1개와 조건 1개로 해결. 서버 대수와 무관 | 만료 시간과 작업 시간의 관계를 설계해야 함                                                                                          |

외부 API를 호출하는 동안 DB 커넥션을 오래 잡지 않으면서 가장 단순한 TTL 방식을 선택했습니다.

### 해결 1: 분석 시작 시각 기록 + 만료된 락 재획득

`analysisStartedAt`(`timestamptz`, nullable) 컬럼을 추가하고, 선점 조건을 다음과 같이 바꿨습니다.

> `IDLE`이거나, `PROCESSING`이면서 시작 후 5분이 지난 경우 선점 가능

```ts
const result = await this.diaryRepository.update(
  [
    { id: diaryId, analysisStatus: 'IDLE' },
    {
      id: diaryId,
      analysisStatus: 'PROCESSING',
      analysisStartedAt: LessThanOrEqual(expireBefore),
    },
  ],
  { analysisStatus: 'PROCESSING', analysisStartedAt: now /* ... */ },
);
return result.affected === 1 ? now : null;
```

- TypeORM `update()`의 조건에 배열을 넘기면 OR 조건으로 변환됩니다.
  QueryBuilder로 SQL을 직접 작성하는 방법도 검토했지만, 기존 `update()` 스타일을 유지할 수 있어 배열 방식을 선택했습니다.
- 여전히 UPDATE 한 문장이므로 2번의 원자성이 그대로 유지됩니다.
- 반환값을 `boolean`에서 획득한 락의 시작 시각(`Date | null`)으로 바꿨습니다. 이 값은 해제할 때 소유권을 증명하는 데 쓰입니다.

실제로 실행된 SQL:

```sql
UPDATE "diaries" SET "analysisStatus" = $1, "analysisStartedAt" = $2, "updatedAt" = "updatedAt"
WHERE (("id" = $3 AND "analysisStatus" = $4)
    OR ("id" = $5 AND "analysisStatus" = $6 AND "analysisStartedAt" <= $7))
```

### 해결 2: 이전 작업이 새 작업의 락을 해제하지 못하게 보호

TTL을 도입하면 새로운 경쟁 조건이 생깁니다.

1. 작업 A가 락을 획득했지만 지연됨
2. 5분이 지나 작업 B가 락을 재획득
3. A가 뒤늦게 끝나 `finishAnalysis` 실행
4. B의 락이 해제됨 → 또 다른 요청이 들어올 수 있음

해제 조건에 "내가 획득한 시각"을 포함해 해결했습니다.

```ts
await this.diaryRepository.update(
  { id: diaryId, analysisStatus: 'PROCESSING', analysisStartedAt: startedAt },
  { analysisStatus: 'IDLE', analysisStartedAt: null /* ... */ },
);
```

### 해결 3: OpenAI 호출 시간을 락 만료 시간보다 짧게

작업이 락 만료(5분)보다 오래 걸리면 두 작업이 동시에 실행될 수 있습니다.
OpenAI 클라이언트에 상한을 설정했습니다.

```ts
new OpenAI({ apiKey, timeout: 60_000, maxRetries: 0 });
```

SDK의 기본 재시도는 2회라서, 최악의 경우 60초 × 3회에 대기 시간까지 더해집니다.
`maxRetries: 0`으로 최대 작업 시간을 명확하게 했습니다.

### 설계 시 고려한 점: 시간 정밀도와 시계 기준

락 시각을 DB(`NOW()`)에서 만들면 문제가 생길 수 있습니다.

- PostgreSQL은 마이크로초, JS `Date`는 밀리초 정밀도입니다.
  DB 값을 JS로 가져와 다시 `=`로 비교하면 불일치가 생길 수 있고, 그러면 락이 영원히 해제되지 않는 새로운 고착이 발생합니다.

그래서 애플리케이션에서 만든 `Date`를 저장하고 그대로 반환하도록 설계했습니다.
저장한 값과 비교할 값이 같은 `Date`이므로 정밀도 불일치가 생기지 않습니다.

- 트레이드오프: 서버가 여러 대이면 서버 간 시계 차이가 생길 수 있습니다.
  NTP로 동기화된 시계의 오차는 보통 1초 미만이고 락 만료는 5분이므로, 영향이 없다고 판단했습니다.

- 동시 요청 시 OpenAI 1회 호출, 나머지 요청은 409
- OpenAI가 실패해도 획득한 시각 그대로 `finishAnalysis` 호출 (`toHaveBeenCalledWith(4, startedAt)`)

테스트가 실제로 버그를 잡는지 확인하기 위해 `finishAnalysis` 호출을 일부러 주석 처리했고,
'OpenAI 실패' 테스트와 '동시 요청' 테스트 2개가 실패하는 것을 확인했습니다.

## 4. 락 상태 변경이 다이어리 수정 시각을 바꾸는 문제

### 문제

3번을 검증하면서 실행 SQL을 확인하다가, 코드에 작성하지 않은 구문이 들어 있는 것을 발견했습니다.

```sql
UPDATE "diaries" SET "analysisStatus" = $1, ..., "updatedAt" = CURRENT_TIMESTAMP WHERE ...
```

사용자가 다이어리를 수정하지 않았는데도 AI 분석만 실행하면 다이어리의 "마지막 수정 시각"이 바뀌고 있었습니다.
3번 이전의 락 코드부터 있던 문제입니다.

### 원인 분석

엔티티의 `@UpdateDateColumn`은 `update()`를 실행할 때마다 TypeORM이 `updatedAt`을 자동으로 갱신합니다.
TypeORM 소스(`UpdateQueryBuilder`)를 보면, set에 `updatedAt`이 없을 때 `"updatedAt" = CURRENT_TIMESTAMP`를 추가합니다.

### 해결

set에 `updatedAt`을 직접 넣되, 기존 값 그대로 넣도록 했습니다.

```ts
updatedAt: () => '"updatedAt"', // SQL: "updatedAt" = "updatedAt" → 변화 없음
```

- `() => '...'`는 값이 아닌 SQL 표현식을 그대로 넣는 TypeORM 문법입니다.
- `"updatedAt"`의 큰따옴표는 PostgreSQL에서 대소문자가 섞인 컬럼명을 가리키기 위해 필요합니다.
- 락 획득(`tryStartAnalysis`)과 해제(`finishAnalysis`) 두 곳 모두 적용했습니다.

다른 방법으로 락 전용 테이블을 분리하는 것도 고려했지만, 현재 규모에서는 과하다고 판단했습니다.

### 검증 (실제 PostgreSQL)

| 시나리오                               | 기대                             | 결과 |
| -------------------------------------- | -------------------------------- | ---- |
| 분석 성공 전후 `updatedAt`             | 변화 없음                        | 통과 |
| 분석 실패(OpenAI 503) 전후 `updatedAt` | 변화 없음                        | 통과 |
| 락 획득·해제 SQL                       | 모두 `"updatedAt" = "updatedAt"` | 통과 |
| (회귀) 사용자가 다이어리를 직접 수정   | `updatedAt` 갱신됨               | 통과 |

마지막 항목은 반대 방향 확인입니다. 수정 시각이 아예 안 바뀌게 망가뜨린 것이 아니라,
락 변경에만 정확히 적용되었는지 확인했습니다.

## 5. OpenAI 호출 실패 시 오류 처리

### 문제

OpenAI 호출 실패를 그대로 노출하거나, 실패한 뒤에 분석 진행 상태가 남아 있으면 사용자가 다시 시도할 수 없습니다.

### 해결

- [`AiService`](../src/ai/ai.service.ts)의 `try/catch`에서 오류를 NestJS `Logger`로 기록
- 클라이언트에는 `ServiceUnavailableException`(HTTP 503)으로 응답
- SDK 타임아웃 60초, 자동 재시도 0회 ([3번](#해결-3-openai-호출-시간을-락-만료-시간보다-짧게) 참고)
- 분석 서비스의 `try/finally`로 실패 시에도 락 해제

### 검증

- Jest: 503 발생, 분석 결과 `create()`/`save()` 미호출, `finishAnalysis(diaryId, startedAt)` 호출
- 실제 PostgreSQL: 503 응답, 분석 결과 0건, 상태 `IDLE` 복구 ([3번 검증](#검증) 참고)

## 6. 다이어리 수정 시 기존 AI 분석과의 정합성

### 문제

본문을 수정한 뒤에도 이전 본문의 AI 분석이 남아 있으면 다이어리 내용과 분석 결과가 맞지 않게 됩니다.
반대로 제목만 바꿨는데 분석을 삭제하면 다시 분석하느라 OpenAI 비용이 듭니다.

### 처음 구현

- 본문이 전달되었고 실제로 기존 본문과 다를 때만 분석 삭제
- 다이어리 수정과 분석 삭제를 `DataSource.transaction()`으로 묶어 하나만 반영되는 상황 방지
- 제목만 수정하면 기존 분석 유지

### 그 뒤에 발견한 문제

**분석 중에 본문을 고치면 옛 본문의 분석이 저장됨**

1. 분석 요청이 락을 잡고 수정 전 본문을 OpenAI에 보냄
2. 응답을 기다리는 사이 본문 수정. 아직 저장된 분석이 없어서 지울 것도 없음
3. 분석이 끝나면서 수정 전 본문의 분석이 저장됨

**분석 중에 제목만 고쳐도 분석 락이 풀림**

수정 코드는 다이어리를 먼저 읽고, 요청 값을 합친(`merge`) 뒤 `save()`했습니다.
`save()`는 저장 직전에 DB의 현재 행을 다시 읽어 엔티티와 값이 다른 컬럼을 모두 UPDATE합니다.
그래서 엔티티를 읽은 뒤에 분석이 시작되면, 엔티티에 남아 있던 `analysisStatus = 'IDLE'`, `analysisStartedAt = null`이 DB의 `PROCESSING`을 덮어씁니다.
락이 풀리면 같은 다이어리에 분석이 또 시작될 수 있습니다.
TypeORM 소스(`SubjectChangedColumnsComputer`)를 따라가 보고 확인했습니다.

### 해결

```ts
// src/diary/diary.service.ts - updateDiary() 트랜잭션 안
const currentDiary = await diaryRepository.findOne({
  where: { id: diaryId },
  lock: { mode: 'pessimistic_write' }, // SELECT ... FOR UPDATE
});

if (isContentChanged && isAnalyzing) {
  throw new ConflictException('AI 분석이 진행 중이라 ...');
}

await diaryRepository.update({ id: diaryId }, updateDiaryDto);

if (isContentChanged) {
  await diaryAnalysisRepository.delete({ diary: { id: diaryId } });
}
```

- `save()` 대신 `update()`: 요청에 들어온 필드만 SET에 들어가고(`undefined` 필드는 빠짐), 락 컬럼은 건드리지 않습니다.
- 행 잠금: 수정 트랜잭션이 다이어리 행을 잡고 있는 동안 `tryStartAnalysis`의 조건부 UPDATE는 기다립니다. 그래서 "분석 중인지" 확인한 값이 수정을 마칠 때까지 바뀌지 않습니다. 잠금은 OpenAI를 기다리지 않는 짧은 트랜잭션 안에서만 걸리므로 3번에서 피하려던 커넥션 점유 문제는 생기지 않습니다.
- 분석 중 본문 수정은 409: `PROCESSING`이고 시작한 지 5분이 안 됐으면 본문 수정을 거절합니다. 5분 기준은 `tryStartAnalysis`와 같은 상수(`ANALYSIS_LOCK_TTL_MS`)를 씁니다. 제목·날짜만 고치는 요청은 허용합니다.
- 락을 잡은 뒤 다시 읽기: 분석 요청은 소유권 확인을 위해 락을 잡기 전에 다이어리를 한 번 읽습니다. 그 사이에 본문이 바뀔 수 있어서, 락을 잡은 뒤 다시 읽은 본문을 OpenAI에 보냅니다. 락이 유효한 동안(5분)은 위의 409 때문에 본문이 바뀌지 않습니다.

### 검토한 다른 방법

| 방법                                                     | 고르지 않은 이유                                                                 |
| -------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 분석 저장 직전에 행을 잠그고 본문 · 락이 그대로인지 확인 | 본문이 바뀌었으면 저장을 거절하게 되는데, 그때는 이미 OpenAI 비용을 쓴 뒤입니다. |
| 다이어리에 버전 컬럼 추가                                | 마이그레이션이 필요하고, 본문 수정을 막는 것만으로 충분했습니다.                 |

대신 사용자는 분석이 끝날 때까지(OpenAI 호출 상한 60초) 본문을 고칠 수 없습니다. 분석을 요청하면 보통 결과를 기다리므로 받아들일 수 있다고 봤습니다.

### 검증

- 단위 테스트: 제목만 변경 → 분석 삭제 미호출 / 본문 변경 → 분석 삭제 1회 호출
- 409 조건을 처음에 분석 삭제 조건 자리에 잘못 넣었는데, 본문 변경 테스트가 실패해서 바로 찾았습니다.
- 분석 중 409와 락 만료 후 수정 허용은 DB에서 `analysisStatus`, `analysisStartedAt`을 직접 바꿔 Postman으로 확인할 예정입니다. OpenAI 응답이 빨라서 탭 두 개로는 타이밍을 맞추기 어려웠습니다.

관련 코드: [`diary.service.ts`](../src/diary/diary.service.ts)의 `updateDiary()`, [`diary_analysis.service.ts`](../src/diary_analysis/diary_analysis.service.ts)의 `createAnalysis()`
관련 테스트: [`diary.service.spec.ts`](../src/diary/diary.service.spec.ts) (Mock 기반 분기 검증)

## 7. DB UNIQUE 위반이 500으로 응답되는 문제 (전역 예외 필터)

### 문제

같은 이메일로 회원가입 요청이 동시에 들어오면, 한 요청이 `500 Internal server error`를 받았습니다.

1. 두 요청 모두 서비스의 이메일 중복 조회를 통과 (아직 저장된 사용자가 없음)
2. 먼저 INSERT한 요청은 성공
3. 나중 요청은 `users.email`의 UNIQUE 제약 위반(PostgreSQL `23505`)으로 실패 → 500

클라이언트 입장에서는 "이미 존재하는 데이터"인데 서버 장애처럼 보이고, 서버 쪽에서도 진짜 장애와 구분되지 않습니다.
[남은 과제](#락-만료-후-이전-작업의-결과-저장)에 적어 둔 "락 만료 후 늦게 끝난 분석 저장"도 필터 적용 전에는 같은 경로로 500이 났습니다.

또한 에러 응답의 필드 구성이 예외 종류마다 달랐습니다.
`HttpException`은 `{ statusCode, message, error }`, 처리되지 않은 예외는 `{ statusCode, message }`였고,
어느 쪽에도 요청 경로와 시각이 없어 클라이언트가 보고한 에러를 서버 로그와 맞춰 보기 어려웠습니다.

### 원인 분석

- Nest 기본 예외 처리기는 `HttpException` 계열만 상태 코드를 해석하고, 그 외 예외는 모두 500으로 응답합니다.
- TypeORM이 던지는 `QueryFailedError`는 `HttpException`이 아니므로, UNIQUE 위반도 500이 됩니다.
- 서비스의 사전 중복 조회만으로는 동시 요청을 막을 수 없습니다. 조회와 INSERT 사이에 다른 요청이 끼어들 수 있기 때문입니다.
  최종 방어선은 DB의 UNIQUE 제약이고, 그 제약 위반을 HTTP 응답으로 어떻게 바꿀지가 문제였습니다.

### 해결 방안 비교

**1) 23505를 어디서 처리할지**

| 방안                                          | 장점                               | 단점                                                                            |
| --------------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------- |
| 서비스마다 `try/catch` 후 `ConflictException` | 상황별로 구체적인 메시지           | 회원가입, 분석 저장 등 UNIQUE가 걸린 모든 저장 지점에 반복. 하나라도 빠지면 500 |
| **전역 예외 필터에서 일괄 409 (선택)**        | 한 곳에서 처리, 놓친 경로까지 방어 | 메시지가 일반적 (어떤 값이 중복인지 알려 주지 않음)                             |

필터를 기본 안전망으로 두고, 구체적인 메시지가 필요한 경로가 생기면 그때 서비스에서 처리를 추가하기로 했습니다.

**2) 필터 등록 방식**

| 방안                                           | 장점                                                           | 단점                                                                                                        |
| ---------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `main.ts`의 `app.useGlobalFilters()`           | 코드가 직관적                                                  | e2e 테스트는 `AppModule`로 앱을 만들고 `main.ts`를 실행하지 않으므로, 테스트 셋업에 같은 등록을 반복해야 함 |
| **`AppModule`의 `APP_FILTER` provider (선택)** | `AppModule`을 import하면 테스트 앱에도 자동 적용, DI 사용 가능 | 어느 모듈에 등록해도 전역이라 위치를 `AppModule`로 정해 두어야 함                                           |

**3) 구현 방식**

| 방안                                                    | 장점                                        | 단점                                                 |
| ------------------------------------------------------- | ------------------------------------------- | ---------------------------------------------------- |
| `BaseExceptionFilter` 상속 + `@Catch(QueryFailedError)` | 코드가 짧음, 나머지는 Nest 기본 동작 재사용 | 응답 형식이 Nest 기본값에 고정 (경로·시각 추가 불가) |
| **`@Catch()` 전체 예외 필터 직접 구현 (선택)**          | 모든 에러 응답 형식을 한 곳에서 통제        | 코드량 증가, 기본 동작을 직접 재현해야 함            |

에러 응답 형식 통일도 목표였기 때문에 직접 구현을 선택했습니다.

### 해결

[`AllExceptionFilter`](../src/common/exception-filter/http.exception-filter.ts)를 `@Catch()`로 만들어 모든 예외를 받고, 세 갈래로 나눕니다.

| 예외                                                                | 응답                                                                      |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `HttpException` 계열 (NotFound, Conflict, ValidationPipe, Guard 등) | 원래 상태 코드와 메시지 유지. ValidationPipe의 `string[]` 메시지도 그대로 |
| `QueryFailedError` + `driverError.code === '23505'`                 | **409**, `이미 존재하는 데이터입니다.`                                    |
| 그 외 모든 예외                                                     | **500**, 고정 문구 `서버 내부 오류가 발생했습니다.`                       |

응답 형식:

```json
{
  "statusCode": 409,
  "error": "Conflict",
  "message": "이미 존재하는 데이터입니다.",
  "path": "/auth/signup",
  "timestamp": "2026-11-04T05:12:30.123Z"
}
```

설계 시 고려한 점:

- `unknown`으로 받기: 어떤 예외가 올지 모르므로 `any` 대신 `unknown`으로 받고 `instanceof`로 좁힙니다.
- 500의 원본 메시지 숨김: DB 에러 메시지에는 테이블·컬럼 이름 같은 내부 정보가 들어 있을 수 있어서 응답에는 고정 문구만 보냅니다.
  원본은 서버 로그에 남깁니다.
- 500만 로그: `METHOD 경로 상태코드`와 스택을 `Logger.error`로 남깁니다. 4xx는 클라이언트 요청 문제라 로그에서 제외해 진짜 장애가 묻히지 않게 했습니다.
  요청 본문은 사용자 입력 원문이므로 로그에 남기지 않습니다.
- ISO 8601 시각: 서버 시간대 설정과 관계없이 어느 언어에서든 파싱됩니다.
- `APP_FILTER` 등록: [`app.module.ts`](../src/app.module.ts)의 `providers`에 등록했습니다.

### 검증 (Postman / curl)

| 요청                                                       | 결과                                                                   |
| ---------------------------------------------------------- | ---------------------------------------------------------------------- |
| 형식이 틀린 회원가입 요청                                  | 400, `message`가 필드별 에러 배열                                      |
| 토큰 없이 `GET /users/me`                                  | 401                                                                    |
| 존재하지 않는 다이어리 조회                                | 404                                                                    |
| 같은 이메일로 순차 회원가입 2회                            | 409, `이미 사용중인 이메일입니다.` (서비스의 사전 조회에서 걸림)       |
| **같은 이메일로 동시 회원가입 2회** (curl 백그라운드 실행) | 1건 201, 1건 **409 `이미 존재하는 데이터입니다.`** (필터의 23505 갈래) |

모든 응답에 `statusCode`, `error`, `message`, `path`, `timestamp`가 포함되는 것을 확인했습니다.

- 필터 단위 테스트는 작성하지 않았습니다. 위 시나리오는 실제 PostgreSQL 기반 e2e 테스트를 도입할 때 자동화할 예정입니다.
- 락 만료 후 분석 결과 저장 시나리오는 직접 재현하지 않았습니다. 같은 `QueryFailedError(23505)` 갈래를 거치므로 409로 응답됩니다.

### 남은 한계

- 23505 응답 메시지가 일반적이라 어떤 값이 중복되었는지 알려 주지 않습니다.
- 문자열로 만든 `HttpException`은 `error`에 클래스 이름(`HttpException`)이 들어가고, 객체로 만든 예외는 `Not Found` 같은 문구가 들어가 `error` 값의 형식이 섞일 수 있습니다.

## 8. IP 기반 요청 제한으로는 사용자별 OpenAI 비용을 통제할 수 없는 문제

### 문제

AI 분석 API는 `@nestjs/throttler`로 IP당 1분에 5회만 막고 있었습니다.
이 방식으로는 OpenAI 호출 비용을 사용자 단위로 통제할 수 없었습니다.

- IP 단위로 셈: 같은 IP(회사·학교 공용 네트워크)를 쓰는 사용자들이 한도를 나눠 쓰고, 반대로 한 사용자가 IP를 바꾸면 한도를 우회합니다.
- 짧은 시간 창만 존재: 1분에 5회를 지키기만 하면 하루 동안 7,000회 넘게 호출할 수 있습니다.
- HTTP 요청을 셈: 이미 분석이 있어 OpenAI를 호출하지 않고 기존 결과를 반환하는 요청, 404·409로 끝나는 요청도 횟수에 포함됩니다.

### 원인 분석

- throttler는 가드에서 동작하므로 HTTP 요청 단위로만 셀 수 있습니다. 실제 OpenAI 호출 여부는 서비스 로직 안에서 결정되기 때문에 가드는 알 수 없습니다.
- `getTracker`를 재정의하면 사용자 ID로 셀 수는 있습니다. 하지만 전역 가드(`APP_GUARD`)인 `ThrottlerGuard`가 컨트롤러의 `AccessTokenGuard`보다 먼저 실행되므로, 그 시점에는 `req.user`가 아직 없습니다.
- throttler의 기본 저장소는 Node 프로세스 메모리입니다. 서버를 재시작하면 카운트가 초기화되고, 서버를 여러 대로 늘리면 서버마다 따로 세어 한도가 대수만큼 늘어납니다.

### 해결 방안 비교

**1) 어디서 셀지**

| 방안                                        | 장점                                                             | 단점                                                |
| ------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------- |
| throttler `getTracker`로 사용자별 제한      | 기존 설정 재사용                                                 | 가드 실행 순서 문제, OpenAI를 부르지 않는 요청도 셈 |
| **서비스에서 OpenAI 호출 직전에 셈 (선택)** | 기존 분석 반환·404·409처럼 OpenAI까지 가지 않는 요청은 세지 않음 | 서비스에 제한 로직이 추가됨                         |

**2) 카운트를 어디에 저장할지**

| 방안                                       | 장점                                                      | 단점                                                                                 |
| ------------------------------------------ | --------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| PostgreSQL에서 최근 24시간 분석 행 `COUNT` | 인프라 추가 없음                                          | 조회 후 비교 사이에 동시 요청이 끼어들어 한도 초과 가능, 실패한 호출은 기록되지 않음 |
| 서버 메모리                                | 가장 빠름                                                 | 재시작 시 초기화, 서버 여러 대에서 공유 불가                                         |
| **Redis (선택)**                           | 서버 밖 공유 저장소, `INCR`이 원자적, `TTL`로 자동 초기화 | Redis 컨테이너와 `ioredis` 의존성 추가                                               |

Redis 클라이언트는 `ioredis`를 썼습니다. `@nestjs/cache-manager`는 get/set 중심이라 "읽기 → +1 → 저장" 사이에 동시 요청이 끼어들 수 있어 카운터에는 맞지 않았습니다.

**3) INCR과 EXPIRE를 어떻게 묶을지**

| 방안                                        | 장점                                                          | 단점                                                                                   |
| ------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `INCR` 후 결과가 1이면 `EXPIRE`를 따로 호출 | 코드가 단순                                                   | 두 명령 사이에 서버가 죽으면 만료 없는 키가 남아 그 사용자가 **영구 차단**             |
| `MULTI`로 `INCR` + `EXPIRE key 86400 NX`    | 원자적, 만료가 없을 때만 설정                                 | `EXPIRE`의 `NX` 옵션은 Redis 7.0 이상 필요, `EXEC` 결과 배열에서 `INCR` 값을 꺼내야 함 |
| **Lua 스크립트를 `EVAL`로 실행 (선택)**     | 원자적 + 스크립트 안에서 조건 분기 가능, Redis 버전에 덜 의존 | Lua 문법을 알아야 함                                                                   |

[Redis INCR 문서의 rate limiter 예제](https://redis.io/docs/latest/commands/incr/)가 첫 번째 방식의 race condition을 지적하고 같은 Lua 스크립트를 보여 주고 있어서, 그 스크립트를 그대로 썼습니다.

### 해결

[`RedisModule`](../src/redis/redis.module.ts)에서 `ConfigService`로 `REDIS_HOST`, `REDIS_PORT`를 읽어 ioredis 클라이언트를 `REDIS_CLIENT` 토큰으로 등록했습니다.
[`DiaryAnalysisService`](../src/diary_analysis/diary_analysis.service.ts)는 이 클라이언트를 주입받아 OpenAI 호출 직전에 횟수를 차감합니다.

```lua
local count = redis.call('INCR', KEYS[1])
if count == 1 then
  redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return count
```

- 키: `ai-quota:{userId}`. 사용자마다 따로 셉니다.
- 한도: 첫 호출부터 24시간 동안 10회(`AI_DAILY_LIMIT`). 넘으면 429 `TOO_MANY_REQUESTS`를 던집니다.
- 호출 위치: 기존 분석 조회와 락 획득 후 재조회를 모두 통과한 다음, `aiService.analyzeDiary` 바로 앞입니다.
  기존 분석을 반환하는 요청은 차감하지 않고, 429도 `try` 안에서 던져지므로 `finally`에서 분석 락 해제를 시도합니다.
  단, 먼저 `INCR`한 뒤 한도와 비교하므로 한도를 넘어 거절된 요청도 카운터는 증가합니다(OpenAI는 호출하지 않음).
- `eval` 반환값 검증: ioredis는 `eval` 결과를 `unknown`으로 반환하므로 `typeof`로 숫자인지 확인한 뒤 사용합니다.
- IP throttler는 유지: 짧은 시간에 몰리는 요청(버스트) 방어용으로 그대로 둡니다. 두 제한은 역할이 다릅니다.
- Redis 포트: `docker-compose.yaml`에서 `127.0.0.1:6379`로만 열어, 비밀번호 없는 Redis가 외부 네트워크에 노출되지 않게 했습니다.

### 검증 (Postman)

`AI_DAILY_LIMIT`을 임시로 2로 낮추고, 날짜가 다른 다이어리 3개에 분석을 요청했습니다.

| 요청                | 결과                                      |
| ------------------- | ----------------------------------------- |
| 1번째 다이어리 분석 | 200, 분석 결과 반환                       |
| 2번째 다이어리 분석 | 200, 분석 결과 반환                       |
| 3번째 다이어리 분석 | **429**, 한도 초과 메시지 (OpenAI 미호출) |

응답은 [7번](#7-db-unique-위반이-500으로-응답되는-문제-전역-예외-필터) 전역 예외 필터 형식(`statusCode`, `error`, `message`, `path`, `timestamp`)을 그대로 따랐습니다.

- 기존 `DiaryAnalysisService` 단위 테스트에 Redis mock(항상 1 반환)을 추가해, 기존 서비스 분기(기존 분석 재사용, OpenAI 실패 시 미저장, 락을 못 얻은 요청은 OpenAI 미호출)가 유지되는 것을 확인했습니다.
  이 테스트는 락 획득 결과를 mock으로 정해 서비스 분기만 검증하며, 실제 DB 락이나 Redis의 동시성을 입증하지는 않습니다.
- 한도 초과 분기(429, OpenAI 미호출, 락 해제)는 `eval`이 11을 반환하도록 mock하면 단위 테스트로 검증할 수 있지만, 아직 작성하지 않았습니다(이번에는 Postman으로 확인).
- Lua 스크립트와 `TTL` 동작은 mock으로 재현할 수 없어, 실제 Redis 기반 테스트를 도입할 때 자동화할 예정입니다.

### 남은 한계

- 고정 윈도우: 첫 호출부터 24시간을 셉니다. 첫 호출이 구간을 시작하므로, 만료 직전에 남은 9회와 직후 새 구간의 10회를 합쳐 짧은 시간에 최대 19회까지 가능합니다.
- 선차감: OpenAI 호출 전에 1회를 차감하고, 호출이 실패해도 돌려주지 않습니다. 타임아웃이면 실제 과금 여부를 알 수 없고, 환불 시점에 이미 새 24시간 구간이 시작됐을 수도 있기 때문입니다.
- Redis 장애 시 지연 후 500: 카운트를 확인할 수 없으면 OpenAI 호출을 막는 쪽(fail-closed)을 택했습니다. 비용 보호가 우선이기 때문입니다.
  다만 ioredis 기본 설정(재연결 동안 명령을 대기열에 보관하고 재시도)을 그대로 써서, 명령이 최종 실패할 때까지 응답이 지연될 수 있습니다. 요청 시간 제한과 503 구분 응답은 개선 과제입니다.
- 카운트 영속성: 앱 서버를 재시작해도 카운트는 유지됩니다. 하지만 Redis의 영속 볼륨과 저장 정책을 명시하지 않아, Redis 쪽 데이터 보존은 보장하지 않습니다.

## 남은 과제

### 락 만료 후 이전 작업의 결과 저장

락이 만료되어 작업 B가 재획득한 뒤, 늦게 끝난 작업 A가 분석 결과를 저장하는 경우입니다.

- OpenAI 호출 상한(60초)이 락 만료(5분)보다 짧아서 보통은 생기지 않습니다. 다만 Redis 대기나 DB 작업까지 포함한 전체 시간에는 상한이 없습니다.
- 두 작업이 모두 저장하려 하면 `diary_analyses.diaryId`의 UNIQUE 제약으로 분석 결과는 1건만 저장됩니다.
- 다만 락이 만료되면 본문 수정도 허용되므로(6번), 그 사이 본문이 바뀌었다면 늦게 끝난 작업이 옛 본문의 분석을 저장할 수 있습니다.
- 나중에 저장하는 쪽은 UNIQUE 위반(`23505`)을 받지만, [7번](#7-db-unique-위반이-500으로-응답되는-문제-전역-예외-필터) 전역 예외 필터 적용 후 500이 아닌 409로 응답합니다.

개선 방향: 409 대신 이미 저장된 분석 결과를 반환하면 클라이언트가 재조회하지 않아도 됩니다. 필요해지면 분석 서비스에서 `23505`를 직접 처리하는 방식을 검토합니다.

### 기타

- 락 재획득(TTL 발동)이 일어났을 때 로그를 남겨 운영 중 관찰할 수 있도록 개선
- 실제 PostgreSQL 검증을 저장소에 포함해 자동화
