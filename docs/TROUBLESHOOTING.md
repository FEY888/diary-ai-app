# Diary AI 트러블슈팅

개발하면서 막혔던 부분과 어떻게 고쳤는지 기록했습니다.

## 1. 다이어리 목록 조회 성능 개선 (복합 인덱스)

다이어리가 많아지면 목록 조회에 얼마나 걸릴지 궁금해서 로컬 DB에 데이터를 넣고 측정했습니다. 당시 `diaries`에는 기본 키 인덱스만 있었습니다.

`userId`만 인덱스에 넣으면 사용자별로 다이어리를 찾을 수 있지만, 결과를 날짜순으로 정렬하는 작업은 남습니다. `(userId, diaryDate)` 순서로 [복합 인덱스](../src/migrations/1791653488772-AddDiaryUserDiaryDateIndex.ts)를 만들면 한 사용자의 데이터를 날짜순으로 읽을 수 있습니다. 다이어리를 추가하거나 날짜를 바꿀 때 인덱스도 갱신해야 하지만, 자주 쓰는 목록 조회를 먼저 개선하기로 했습니다.

로컬 PostgreSQL 17의 다이어리 100,003건 중 한 사용자의 101건을 조회했습니다. `EXPLAIN (ANALYZE, BUFFERS)`의 실행 시간을 적용 전후 5번씩 기록했습니다.

| | 적용 전 | 적용 후 |
| --- | ---: | ---: |
| 평균 | 15.952 ms | 0.278 ms |
| 중앙값 | 13.740 ms | 0.249 ms |
| 범위 | 11.378~21.507 ms | 0.064~0.591 ms |

이 수치는 페이지 처리(`LIMIT/OFFSET`)와 전체 건수 조회(`COUNT`)를 뺀 SQL 실행 시간입니다. 실행 계획 원문을 남기지 못했고 캐시 상태도 맞추지 않았습니다. 다시 측정할 때는 목록 API가 실행하는 SQL 그대로 비교하고 실행 계획도 함께 저장할 생각입니다.

## 2. AI 분석 중복 요청으로 인한 OpenAI 중복 호출

처음에는 저장된 분석이 있는지 조회한 뒤 OpenAI를 호출했습니다. 같은 다이어리에 요청 두 개가 들어오면 둘 다 분석 결과가 없다고 보고 각각 호출할 수 있었습니다.

`IDLE`인 다이어리를 `PROCESSING`으로 바꾸는 조건부 `UPDATE`를 추가했습니다. 실제로 행을 바꾼 요청만 분석을 진행하고, 나머지 요청은 `409`를 받습니다. 분석을 시작하기 직전에 결과를 한 번 더 조회해 그사이에 저장된 결과가 있으면 재사용합니다.

Jest에서는 락을 얻지 못한 요청이 OpenAI를 호출하지 않는지 확인했습니다. 실제 PostgreSQL에서 요청을 겹쳐 보낸 결과는 [3번](#3-서버-장애-시-분석-락이-해제되지-않는-문제)에 정리했습니다.

## 3. 서버 장애 시 분석 락이 해제되지 않는 문제

락을 `finally`에서 풀어도, 서버가 중간에 종료되거나 해제 시 DB 연결이 끊기면 다이어리가 `PROCESSING`으로 남았습니다.

`SELECT FOR UPDATE`로 분석이 끝날 때까지 행을 잠그는 방법도 검토했습니다. 이 방식은 OpenAI 응답을 기다리는 동안 트랜잭션과 DB 연결을 유지해야 합니다. 그래서 조건부 `UPDATE` 한 번으로 `PROCESSING` 상태와 시작 시각을 기록하고, DB 작업이 끝난 뒤 OpenAI를 호출했습니다.

5분이 지나면 다른 요청이 락을 다시 잡을 수 있게 했습니다. 이때 먼저 시작한 작업이 뒤늦게 끝나 새 작업의 락을 풀 수 있습니다. 그래서 락을 잡을 때 받은 `analysisStartedAt`이 DB에 있는 값과 같을 때만 해제합니다. OpenAI SDK는 타임아웃 60초, 자동 재시도 0회로 설정했습니다.

Redis 도입 전, 실제 PostgreSQL 테스트 DB에서 OpenAI만 가짜 구현으로 바꾸고 임시 스크립트로 확인했습니다. 이 스크립트는 저장소에 포함되어 있지 않습니다.

| 확인한 상황 | 결과 |
| --- | --- |
| 같은 다이어리에 분석 요청 10건 | 가짜 OpenAI 호출 1회, 409 응답 9건, 마지막 상태 `IDLE` |
| 락을 잡은 지 4분 59초 / 5분 1초 | 재획득 실패 / 성공 |
| 이전 작업이 새 작업의 락 해제 시도 | 새 작업의 락 유지 |
| OpenAI 호출 실패 | 503 응답, 저장된 분석 0건, 마지막 상태 `IDLE` |

단위 테스트는 락 획득 결과를 Mock으로 정해 서비스의 동작을 확인합니다. `finishAnalysis()` 호출을 잠시 빼봤을 때 관련 테스트 2개가 실패하는 것도 확인했습니다.

## 4. 락 상태 변경이 다이어리 수정 시각을 바꾸는 문제

락 테스트 중 SQL을 보다가 다이어리 내용을 고치지 않아도 `updatedAt`이 바뀌는 걸 발견했습니다. TypeORM의 `@UpdateDateColumn` 때문에 `update()`에 수정 시각 갱신이 자동으로 붙었습니다.

락을 잡고 풀 때만 `updatedAt: () => '"updatedAt"'`을 넘겨 기존 값을 유지했습니다. 실제 PostgreSQL에서 분석 성공·실패 후 수정 시각이 그대로였고, 사용자가 다이어리를 수정할 때는 갱신되는 것도 확인했습니다.

## 5. OpenAI 호출 실패 시 오류 처리

OpenAI 호출에 실패하면 서버에 오류를 기록하고 클라이언트에는 `503`을 보냅니다. 분석 서비스의 `finally`에서 락 해제를 시도해 사용자가 다시 요청할 수 있게 했습니다.

Jest에서는 실패 시 분석을 저장하지 않고 획득 시각으로 락을 해제하는지 확인했습니다. [3번의 실제 DB 검증](#3-서버-장애-시-분석-락이-해제되지-않는-문제)에서도 실패 후 분석이 남지 않고 `IDLE`로 돌아오는 것을 확인했습니다.

## 6. 다이어리 수정 시 기존 AI 분석과의 정합성

처음에는 본문이 바뀌면 같은 트랜잭션에서 기존 분석을 지웠습니다. 분석 도중 본문을 바꾸면, 그 뒤에 수정 전 본문의 분석이 저장될 수 있었습니다. 제목만 수정하는 경우에도 또 다른 문제가 있었습니다. TypeORM의 `save()`가 먼저 읽어 둔 다이어리 객체의 값으로 새 분석 락까지 덮을 수 있었습니다.

수정 트랜잭션에서 다이어리 행을 잠그고, 분석 락이 유효한 동안 본문 변경에 `409`를 보냅니다. 제목과 날짜는 수정할 수 있습니다. 저장에는 `update()`를 써서 요청으로 받은 필드만 바꾸고, 분석 요청은 락을 잡은 뒤 본문을 다시 읽습니다. 분석 결과를 저장할 때 수정 여부를 확인하는 방법도 생각했지만, 그때는 이미 OpenAI 호출 비용이 든 뒤라 본문 변경을 먼저 막기로 했습니다.

[단위 테스트](../src/diary/diary.service.spec.ts)에서는 제목만 바꾸면 분석이 남고, 본문을 바꾸면 분석이 삭제되는지 확인했습니다. 분석 중 본문 수정이 거절되는 경우와 만료 후 수정이 허용되는 경우는 실제 DB 검증이 남아 있습니다.

## 7. DB UNIQUE 위반이 500으로 응답되는 문제 (전역 예외 필터)

같은 이메일로 동시에 가입하면 두 요청이 모두 사전 중복 조회를 통과할 수 있습니다. 먼저 저장한 요청은 성공하고, 나머지는 DB의 UNIQUE 제약에 걸립니다. 처음에는 이 예외가 `500`으로 응답됐습니다.

전역 예외 필터에서 PostgreSQL의 UNIQUE 위반 코드 `23505`를 `409`로 바꿨습니다. 여러 저장 경로에 같은 예외 처리를 반복하지 않아도 됩니다. 응답에 요청 경로와 시각도 추가해 클라이언트에서 받은 에러를 서버 기록과 맞춰 보기 쉽게 했습니다.

curl로 같은 이메일의 가입 요청 두 개를 동시에 보내 `201` 한 건과 `409` 한 건을 확인했습니다. 이 동시 요청 검증은 수동으로 진행했습니다.

## 8. IP 기반 요청 제한으로는 사용자별 OpenAI 비용을 통제할 수 없는 문제

기존 IP 제한은 HTTP 요청을 셉니다. 저장된 분석을 돌려주는 요청까지 포함되고, 같은 IP를 쓰는 사람끼리 한도를 나눠 쓰게 됩니다.

IP 제한은 짧은 시간에 몰리는 요청을 막는 데 쓰고, OpenAI 호출 직전에 Redis에서 사용자별 횟수를 셌습니다. 첫 호출부터 24시간 동안 사용자당 10회까지 허용합니다. `INCR`과 `EXPIRE`를 따로 실행하면 두 명령 사이에 서버가 멈춰 만료 시간이 없는 키가 남을 수 있어서, [Redis 문서의 예제](https://redis.io/docs/latest/commands/incr/)처럼 Lua 스크립트 한 번으로 묶었습니다.

Postman에서 한도를 임시로 2회로 낮추고 서로 다른 다이어리 3개를 분석했습니다. 앞의 두 요청은 `200`, 세 번째는 `429`를 받았습니다. 실제 Redis에서 동시 요청과 TTL을 확인하는 자동 테스트는 아직 없습니다.

현재는 OpenAI 호출 전에 횟수를 차감하고 실패해도 돌려주지 않습니다. 24시간 구간이 바뀌기 직전과 직후에는 짧은 시간에 최대 19번 호출할 수 있습니다. Redis 오류가 나면 OpenAI 호출을 막으며, Redis 데이터 보존을 별도로 설정하지 않아 컨테이너를 다시 만들면 횟수가 초기화될 수 있습니다.

## 9. 로그아웃 후 refresh 토큰 해시가 다시 저장되는 문제

토큰을 재발급할 때는 먼저 DB에서 refresh 토큰 해시를 읽고, 요청으로 받은 토큰과 맞는지 Argon2로 확인합니다. 이때 검증을 마친 직후 로그아웃이 먼저 끝나면 문제가 생길 수 있었습니다. 로그아웃이 해시를 지웠는데도, 이미 진행 중이던 재발급이 뒤늦게 새 해시를 저장할 수 있었기 때문입니다. 이 순서로 처리되면 로그아웃한 뒤에도 새로 받은 refresh 토큰으로 다시 재발급을 요청할 수 있습니다.

그래서 검증에 사용한 해시가 DB에 그대로 있을 때만 새 해시를 저장하도록 바꿨습니다. `UPDATE`의 조건에 사용자 ID와 기존 해시를 함께 넣었습니다. 로그아웃이 먼저 해시를 지웠다면 조건에 맞는 행이 없어서 저장되지 않고, 서버는 `401`을 반환합니다. 두 재발급 요청이 같은 해시를 읽었을 때도 먼저 해시를 바꾼 요청만 성공합니다. [2번의 AI 분석 중복 요청 방지](#2-ai-분석-중복-요청으로-인한-openai-중복-호출)에서 쓴 조건부 업데이트를 여기에도 적용했습니다.

Jest 단위 테스트에서는 해시를 바꾸지 못한 상황을 만들어 재발급이 거절되는지 확인했습니다. 저장 함수에 넘긴 해시가 새 refresh 토큰과 일치하는지도 확인했습니다. 실제 PostgreSQL에서 로그아웃과 재발급이 겹치는 경우는 아직 테스트하지 않았습니다.

## 남은 과제

락을 푸는 동작은 시작 시각으로 확인하지만, 결과를 저장할 때는 아직 같은 확인을 하지 않습니다. 작업이 5분을 넘기고 그사이 다이어리 본문이 바뀌면 옛 본문의 분석이 늦게 저장될 수 있습니다. OpenAI 호출에는 60초 타임아웃을 뒀지만 Redis 대기나 DB 작업을 포함한 분석 전체에는 시간 제한이 없습니다.

다음에는 이 상황을 실제 DB 테스트로 재현하고, 저장 직전에 락 소유권이나 본문 변경 여부를 확인하는 방법을 검토할 계획입니다.
